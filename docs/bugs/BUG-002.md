# BUG-002 — API aceita seis unidades por produto

## Referências

CA10; CT12; RF-008 (cálculo) e RF-024 (pedido). Documentação VZS-142, versão 2.3.0.

## Ambiente

20/10/2026, 16:13 UTC. Playwright 1.64.1, Node 26.8.1, Linux x86_64. Teste direto de API, sem navegador e sem alterar preços. Base: https://verzel-store.qa-test-verzel-store.workers.dev/api.

## Pré-condições e dados

Produto P006 — Kit 3 Pares de Meias, R$ 29,90, quantidade 6. Cliente sintético Maria Silva, maria@example.com, CEP 01310-100. Sem cupom. API sem persistência, conforme documentação.

## Reprodução

1. Enviar POST `/api/carrinho/calcular`, Content-Type application/json, com o corpo abaixo.
2. Repetir em POST `/api/pedidos`.
3. Comparar status, quantidade aceita e número de pedido com o contrato.

```json
{
  "cliente": { "nome": "Maria Silva", "email": "maria@example.com", "cep": "01310-100" },
  "itens": [{ "produtoId": "P006", "quantidade": 6 }]
}
```

## Esperado

Ambas as rotas devem rejeitar com HTTP 422 e `erro.codigo = QUANTIDADE_MAXIMA_EXCEDIDA`. CA10 limita a cinco unidades por produto na interface e na API.

## Obtido

Cálculo: HTTP 200, quantidade 6, subtotal 179,40, frete 19,90 e total 199,30.
Pedido: HTTP 201, número fictício VZ-383198, quantidade 6 e os mesmos valores. A regra pode ser contornada por uma chamada direta à API. Isso é uma validação funcional documentada, sem testes de segurança.

O controle na interface passou em CT11 (RF-053): catálogo e carrinho mantiveram o máximo de cinco unidades e permitiram reduzir para quatro e voltar a cinco. O problema observado é na API.

## Impacto e estado

Severidade proposta: alta; viola uma regra explícita de pedido, permite quantidade superior à política da loja e mantém inconsistência entre UI e API. Prioridade proposta: P1. Reproduzido na rodada de implementação e na suíte completa nas duas rotas. Não atribuir causa a um trecho de código sem acesso à implementação. Confirmado; correção depende da aplicação avaliada.
